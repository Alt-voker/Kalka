# Защита платформы КальКа

Этот документ фиксирует правила работы с кодовой базой, чтобы платформа не "слетала" при следующих доработках.

## 1. Базовое состояние

- Рабочим базовым состоянием считается последний проверенный стабильный коммит.
- Любая новая задача начинается только от этого состояния.
- Перед крупной правкой мы не смешиваем её с другими незавершёнными изменениями.

## 2. Разделение слоёв

- `auth` отвечает только за вход, роли и сессию.
- `business state` отвечает только за рестораны, поставщиков, товары, заказы, техкарты и шаблоны.
- `ui/features` отвечает только за экраны, формы, кнопки и визуальное поведение.
- Один слой не должен перетирать другой пустым или урезанным состоянием.

## 3. Запрет на пустые перезаписи

- Пустой snapshot не может считаться рабочей базой.
- Если в сохранении нет реальных бизнес-данных, такое сохранение отклоняется.
- Если есть рабочие данные, они не должны быть заменены пустым объектом или урезанным профилем.

## 4. Владелец и роли

- Владелец всегда должен иметь полный доступ к панели владельца.
- Нормализация роли не должна понижать владельца до обычного пользователя.
- Для критичных аккаунтов используется резервная проверка по email и по сохранённым правам.

## 5. Изменения только малыми шагами

- Одна правка = одна задача.
- Нельзя одновременно переписывать вход, state, импорт и карточки товаров.
- После каждого изменения проверяются только критичные сценарии, а не весь проект "вслепую".

## 6. Обязательные проверки

- Вход владельца.
- Вход обычного пользователя.
- Видимость панели владельца.
- Навигация по основным вкладкам.
- Поставщики, заказы, корзина, импорт прайсов.
- Экспорт и сохранение данных.

## 7. Резервирование

- Перед рискованной правкой сохраняется рабочая точка восстановления.
- Если новая версия ломает платформу, откат идёт именно к этой точке.
- После отката новые изменения снова вводятся только малыми шагами.

## 8. Запрет на скрытую магию

- Не добавлять скрытые автозаменяющие эвристики, которые меняют название, цену или роль без явного решения пользователя.
- Любая автоматизация должна быть либо подсказкой, либо явно подтверждённым действием.

## 9. Правило для будущих доработок

- Сначала анализ.
- Потом точечное изменение.
- Потом проверка.
- Потом только следующий шаг.
